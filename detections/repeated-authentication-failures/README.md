# DET-AUTH-001 — Repeated Windows Authentication Failures

## Overview

This detection was developed to identify repeated Windows authentication failures that may indicate password-guessing or brute-force activity.

The detection process followed a simple detection-engineering lifecycle:

```text
Detect
  ↓
Investigate
  ↓
Classify
  ↓
Identify False Positive
  ↓
Tune
```

--------------------


Initial Detection

During the laboratory test, multiple Windows authentication failures were generated on CLIENT-22.

The activity triggered custom Wazuh Rule 100100.

The detection was initially interpreted as a possible brute-force attack because multiple authentication failures occurred within the configured threshold.

2. Initial Detection Rule

The initial rule was designed to detect five authentication failures involving the same account within 60 seconds.

Initial Rule
<rule id="100100" level="10" frequency="5" timeframe="60">
  <if_matched_sid>60122</if_matched_sid>
  <same_field>win.eventdata.targetUserName</same_field>
  <description>Windows: Multiple authentication failures for the same account within 60 seconds.</description>
  <mitre>
    <id>T1110</id>
  </mitre>
  <group>authentication_failed,windows,mitre_t1110,</group>
</rule>

Alert Level

5 matching events
Within 60 seconds

The custom rule depends on Wazuh Rule 60122.

This allows the custom rule to build additional correlation logic on top of the existing Wazuh detection.

3. Investigation

The initial alert was not immediately treated as a confirmed attack.

Further investigation was performed using the event details available in Wazuh.

The investigation focused on:

Authentication timing
Source address
Authentication context
Target account
Workstation
Related domain-controller activity
Authentication Timing

The authentication failures occurred during normal working hours in the laboratory scenario.

This was considered supporting context rather than proof that the activity was legitimate.

Time of day alone is not sufficient to classify an authentication event.

Source Address

The event details showed the source address associated with the authentication attempts.

The source was associated with the internal/company lab network rather than an unexpected external source.

This was another contextual indicator that required consideration during investigation.

Logon Type

The detailed Windows event showed:

Logon Type = 2

Logon Type 2 represents Interactive authentication.

The observed event therefore represented a local interactive login rather than the remote/network authentication behavior that this detection was intended to focus on.

4. False Positive Classification

Based on the investigation, the activity was classified as a:

Benign / False Positive

The test was intentionally generated in the controlled laboratory environment to represent repeated incorrect password entry.

The important observation was that the authentication failures were associated with:

Logon Type = 2

which represents local interactive authentication.

Therefore, the original detection was too broad for the intended detection objective.

It detected repeated authentication failures without sufficiently distinguishing between local interactive authentication and remote authentication.

5. Detection Tuning
Why Tune the Detection?

The goal of tuning was to reduce false positives while maintaining coverage for authentication activity that is more relevant to the detection objective.

The investigation identified the authentication context as an important distinguishing factor.

Tuning Decision

The detection was refined to accept:

Logon Type 3
OR
Logon Type 10
Logon Types
Logon Type	Meaning
2	Interactive
3	Network
10	RemoteInteractive / RDP

The tuned detection therefore excludes Logon Type 2 and focuses on network and remote-interactive authentication.

6. Tuned Detection Rule

The final rule is:

<rule id="100100" level="10" frequency="5" timeframe="60">
  <if_matched_sid>60122</if_matched_sid>
  <same_field>win.eventdata.targetUserName</same_field>
  <field name="win.eventdata.logonType">^(3|10)$</field>
  <description>Windows: Multiple remote authentication failures for the same account within 60 seconds.</description>
  <mitre>
    <id>T1110</id>
  </mitre>
  <group>authentication_failed,windows,mitre_t1110,</group>
</rule>

Tuned Rule Explanation

The original detection logic remains:

5 events
+
within 60 seconds
+
same target account

The new condition adds:

Logon Type = 3 OR 10

Therefore, the complete detection logic is:

Windows authentication failure
          ↓
       Rule 60122
          ↓
    Same target account
          ↓
  5 events / 60 seconds
          ↓
   Logon Type 3 or 10
          ↓
      Rule 100100
          ↓
        Alert
Authentication Context Filter
<field name="win.eventdata.logonType">^(3|10)$</field>

This regular expression matches either:

3

or:

10

It does not match:

2

This prevents the tuned detection from treating local interactive authentication failures as equivalent to network or remote-interactive authentication failures.
